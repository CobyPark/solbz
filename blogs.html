무료 AI를 고르기 전에: 웹 채팅, API, 로컬 게이트웨이의 차이

솔루션 비제트 · 문서 기반 활용 가이드 · 2026.10.19

“무료 AI를 업무에 써보고 싶다”는 목표만으로는 도구를 고르기 어렵습니다. 브라우저에서 질문 한 번을 보내는 일과 프로그램에서 문서 백 개를 처리하는 일은 준비할 것이 다르기 때문입니다. 이 글에서는 요금 순위 대신 연결 구조를 기준으로 첫 실험을 설계합니다. 아래의 업무 예시는 설명을 위한 가상 사례이며, 특정 모델의 성능을 실측한 결과는 아닙니다.

화면에서 쓰는 채팅과 프로그램에서 호출하는 API

회의 메모 한 장을 정리하려면 웹 채팅 화면이 간편합니다. 반면 파일이 들어올 때마다 같은 형식으로 요약하려면 프로그램에서 호출하는 API를 검토하게 됩니다. 채팅에서 무료로 쓸 수 있다는 안내가 같은 서비스의 API 무료 사용까지 의미하지는 않습니다. 가입 화면보다 실제 이용할 API의 가격표와 계정 한도를 먼저 확인하세요.

API 실험에는 세 가지 값이 필요합니다. 요청을 보낼 주소, 본인 계정의 API 키, 사용할 모델 ID입니다. 모델의 화면 표시 이름과 요청에 넣는 ID는 다를 수 있습니다. 검색 결과에 나온 옛 이름을 그대로 입력하기보다 현재 모델 상세 화면에서 ID를 복사하면 불필요한 오류를 줄일 수 있습니다.

OpenRouter 무료 모델 첫 호출: 모델 선택부터 Python 응답 확인까지

솔루션 비제트 · 문서 기반 활용 가이드 · 2026.10.19

여러 모델을 시험할 때는 먼저 짧은 질문 한 개를 전송하는 것부터 시작하는 편이 좋습니다. 여기서는 별도 Python 패키지 없이 표준 라이브러리로 요청을 구성합니다. 예제는 연결 구조를 설명하기 위해 작성했으며, 실제 계정으로 유료 또는 무료 추론을 실행해 검증한 결과는 아닙니다.

1. 현재 사용 가능한 무료 모델을 고릅니다

OpenRouter의 무료 모델 목록을 열고 모델 상세 화면에서 ID와 입력·출력 가격을 확인합니다. 무료 변형은 ID의 :free 접미사로 구분할 수 있습니다. 같은 계열이라도 접미사가 다른 ID는 가격이 다를 수 있으므로 전체 문자열을 확인하세요. 무료 목록은 고정되지 않기 때문에 이 예제에는 특정 모델명을 박아 넣지 않았습니다.

모델이 텍스트 입력을 지원하는지 확인한 뒤, 계정에서 API 키를 생성합니다. 무료 모델에도 요청 횟수 제한과 공급자 수용량 문제가 있을 수 있습니다. 계정의 잔액·키 한도·일일 이용량을 먼저 확인하고, 처음부터 여러 작업을 동시에 보내지 마세요.

2. PowerShell에서 현재 세션에만 값을 설정합니다

다음 명령은 Windows PowerShell용입니다. 첫 줄의 입력창에 본인 키를 붙여 넣으면 명령문 자체에 키를 직접 적지 않아도 됩니다. 환경변수는 암호 저장소가 아니므로 화면 공유, 로그 수집, 다른 프로그램 실행 시 취급에 주의하세요. 모델 ID는 방금 확인한 무료 변형으로 바꿉니다.

$env:OPENROUTER_API_KEY = Read-Host "본인 OpenRouter API 키"
$env:OPENROUTER_MODEL = "공식_목록에서_확인한_모델_ID:free"

3. 아래 내용을 first_call.py로 저장하고 실행합니다

import json
import os
import urllib.error
import urllib.request

key = os.environ["OPENROUTER_API_KEY"]
model = os.environ["OPENROUTER_MODEL"]
if not model.endswith(":free"):
    raise SystemExit("이 실습은 :free 모델 ID만 사용합니다.")

payload = {
    "model": model,
    "messages": [{"role": "user", "content": "자료 백업의 목적을 두 문장으로 설명해 줘."}],
    "max_tokens": 256,
    "stream": False,
}
request = urllib.request.Request(
    "https://openrouter.ai/api/v1/chat/completions",
    data=json.dumps(payload).encode("utf-8"),
    headers={"Authorization": "Bearer " + key, "Content-Type": "application/json"},
    method="POST",
)
try:
    with urllib.request.urlopen(request, timeout=60) as response:
        result = json.load(response)
    if result.get("error"):
        raise SystemExit("응답 오류: " + str(result["error"].get("code", "unknown")))
    choices = result.get("choices") or []
    if not choices:
        raise SystemExit("선택 가능한 응답이 없습니다. 모델 상태를 확인하세요.")
    print(choices[0].get("message", {}).get("content") or "텍스트 응답이 비어 있습니다.")
    print("사용량:", result.get("usage", {}))
except urllib.error.HTTPError as error:
    print("HTTP 오류:", error.code)
    print("잔액·키·모델·한도를 확인한 후 다시 시도하세요.")
except (urllib.error.URLError, TimeoutError):
    print("연결 또는 시간 초과 오류: 네트워크와 서비스 상태를 확인하세요.")

python first_call.py로 실행합니다. 답변과 사용량이 나오면 기본적인 요청·응답 흐름을 확인한 것입니다. 모델에 따라 출력 한도를 추론 토큰에 소비해 본문이 짧거나 비어 있을 수 있습니다. 이때 한도만 계속 높이기보다 모델 문서와 응답 상태를 먼저 확인하세요. 한 번의 성공이 장시간 자동 처리의 안정성을 보장하지는 않습니다.

4. 막혔을 때 확인할 순서

KeyError는 환경변수가 현재 Python 프로세스에 전달되지 않았을 때 발생할 수 있습니다. 값을 설정한 같은 터미널에서 실행했는지 확인하세요. HTTP 오류가 나오면 Python 설치부터 다시 하기보다 상태 코드를 기준으로 키 인증, 잔액, 모델 이용 가능 여부를 나누어 점검합니다. 모델 ID 끝에 무료 접미사를 임의로 붙인다고 존재하지 않는 무료 모델이 생기지는 않습니다.

실습이 끝나면 아래 명령으로 이 세션의 값을 제거합니다. 코드를 다른 사람에게 전달할 때는 실제 키와 실행 로그를 제외하고, 설정해야 하는 변수 이름만 안내하세요.

Remove-Item Env:OPENROUTER_API_KEY
Remove-Item Env:OPENROUTER_MODEL

NVIDIA Build 활용 순서: 웹 미리보기에서 API 연결로 넘어가기

솔루션 비제트 · 문서 기반 활용 가이드 · 2026.10.19

NVIDIA Build를 처음 열면 모델 이름과 예제 코드가 많아 어디서 시작해야 할지 막막할 수 있습니다. 처음부터 개발 환경을 복잡하게 구성하기보다, 웹에서 질문을 보내고 같은 모델의 API 예제로 옮겨가는 순서로 접근해 보세요. 이 글은 공식 시작 문서를 기준으로 정리한 절차이며, 개별 모델의 품질이나 무료 제공량을 보증하지 않습니다.

1. 사용할 작업을 한 가지로 제한합니다

가상의 메모를 요약하거나 공개된 제품 설명에서 항목을 추출하는 등 정답을 확인할 수 있는 입력을 준비하세요. 이미지 분석을 하려면 이미지 입력을 지원하는 모델인지 별도로 봐야 합니다. 모델 이름이 비슷하더라도 지원 입력 형식이나 출력 옵션이 다를 수 있습니다. 처음에는 텍스트 한 문단처럼 단순한 입력을 쓰면 연결 문제와 모델 활용 문제를 구분하기 쉽습니다.

2. 모델 페이지의 미리보기에서 결과를 확인합니다

NVIDIA Build 카탈로그에서 모델을 선택하고 Preview가 제공되면 같은 질문을 입력합니다. 모델 카드의 조건, 제공 예제, 이용 관련 안내를 함께 읽으세요. 답변이 생성되는지만 보지 말고 요청한 언어와 출력 형식을 지키는지 확인합니다. 잘못된 내용을 자신 있게 말하는 경우도 있으므로 익숙한 주제로 시작하는 편이 좋습니다.

예를 들어 “장비 점검 완료. 통신 복구 확인. 다음 주 재점검 예정.”이라는 가상의 문장을 주고, “확인된 사실과 예정된 일을 구분해 작성하라”고 요청할 수 있습니다. 결과가 입력에 없는 날짜나 담당자를 만들어내는지 확인하세요. 실제 고객의 장비 기록을 넣을 필요 없이 출력 습관을 먼저 살펴볼 수 있습니다.

3. 같은 모델의 코드에서 연결 값을 확인합니다

OmniRoute는 무엇을 연결할까: 로컬 AI 게이트웨이의 역할과 점검 순서

솔루션 비제트 · 문서 기반 활용 가이드 · 2026.10.19

AI 도구마다 다른 공급자 설정을 입력하다 보면 모델 주소와 키가 뒤섞이기 쉽습니다. 게이트웨이는 클라이언트와 공급자 사이에 공통 연결 지점을 두는 방식입니다. 여기서 다루는 대상은 diegosouzapw/OmniRoute 프로젝트입니다. 이름이 비슷한 OmniRouter 서비스나 다른 프로젝트와는 설치 방법과 조건이 다를 수 있으니 저장소 주소부터 확인하세요.

연결은 세 구간으로 나누어 생각합니다

내 프로그램 → OmniRoute → 연결한 모델 공급자 순서로 요청이 이동합니다. 공급자 키는 게이트웨이가 공급자에 접근할 때 쓰고, 클라이언트용 키는 내 프로그램이 게이트웨이에 접근할 때 씁니다. 두 키를 같은 칸에 무작정 넣으면 인증 오류의 위치를 파악하기 어렵습니다. 설정 메모에는 키 원문 대신 “어느 구간의 키인가”를 적어두세요.

여러 공급자를 연결하기 전에 한 공급자의 모델 한 개로 기본 동작을 확인하는 편이 좋습니다. 자동 전환을 처음부터 켜면 응답이 어느 공급자에서 왔는지와 실패한 연결이 무엇인지 함께 추적해야 합니다. 연결 하나가 검증된 뒤 대체 경로를 추가하면 점검할 조합을 줄일 수 있습니다.

설치 전에 현재 요구사항을 읽습니다

프로젝트는 npm 설치 방법과 대시보드 사용법을 안내합니다. 실행 전 현재 README의 Node.js 지원 버전과 설치 절차를 확인하세요. 이 글에서는 설치 명령을 자동으로 실행하거나 특정 버전의 설치 성공을 주장하지 않습니다. 업무용으로 사용하려면 선택한 버전과 설정을 기록하고, 업데이트 전에 기존 설정으로 복구할 방법을 준비하는 편이 좋습니다.

공식 README의 기본 안내에서는 대시보드가 http://localhost:20128, API 기본 주소가 http://localhost:20128/v1입니다. 포트를 변경했다면 실제 실행 로그에 표시된 값을 사용합니다. 주소를 클라이언트에 입력하기 전에 브라우저에서 대시보드가 열리는지 먼저 확인하세요.

연결이 안 될 때는 바깥쪽부터 다시 설치하지 않습니다

  1. 프로세스가 실행 중인지, 대시보드 주소가 맞는지 확인합니다.
  2. 게이트웨이에서 공급자 연결 상태와 이용 가능 모델을 확인합니다.
  3. 클라이언트의 API 기본 주소, 클라이언트용 키, 모델 식별자를 대조합니다.
  4. 짧은 질문 한 개를 보내고 게이트웨이와 공급자 양쪽의 사용 기록을 확인합니다.

대시보드는 열리는데 답변이 없으면 게이트웨이 실행 자체보다 공급자 인증이나 모델 설정을 살펴볼 단계일 수 있습니다. 반대로 대시보드도 열리지 않으면 포트 충돌과 프로세스 종료부터 봅니다. 매번 모든 프로그램을 재설치하는 것보다 실패한 구간 하나를 좁혀가는 방식이 설정 손실을 줄입니다.

자동 전환에도 비용과 데이터 경로가 있습니다

무료 모델이 막혔을 때 유료 모델로 전환하도록 설정하면 실제 비용이 발생할 수 있습니다. 무료 실험에서는 무료 조건을 확인한 연결만 선택하고, 대체 경로도 같은 기준으로 검토하세요. 게이트웨이가 외부 공급자의 한도를 없애주는 것은 아닙니다. 공급자가 허용한 사용 범위 안에서 대기와 재시도를 설계해야 합니다.

외부로 전송할 수 없는 문서를 넣기 전에는 선택한 공급자와 저장되는 로그를 확인해야 합니다. 로컬 대시보드를 인터넷에 공개할 필요가 없는 개인 실습이라면 외부 포트 개방 없이 진행하세요. 연결이 정상이라는 확인과 조직의 문서 취급 기준을 충족한다는 판단은 각각 기록하는 것이 좋습니다.

AI API가 멈췄을 때: 401·402·403·429 오류를 나누어 확인하는 법

솔루션 비제트 · 문제 해결 가이드 · 2026.10.19

어제까지 되던 API가 멈추면 먼저 모델을 바꾸거나 프로그램을 다시 설치하기 쉽습니다. 하지만 인증 문제, 사용량 제한, 공급자 장애는 해결 방법이 다릅니다. 아래 표는 HTTP API 문제를 좁히기 위한 출발점입니다. 상태 코드의 세부 의미는 서비스마다 다르므로 실제 응답 본문과 해당 공급자의 문서를 함께 확인하세요.

오류에 따라 다음 행동을 다르게 정하기
증상먼저 볼 항목다음 행동
401키 누락, 만료, 잘못된 인증 대상현재 요청 주소와 키 발급 서비스를 대조
402잔액, 키별 비용 한도, 실행 중 요청의 예상 비용계정과 오류 메타데이터를 확인
403접근 정책, 권한, 조직 예산 제한차단 사유에 맞는 설정 점검
429분당·일일 한도, 공급자 처리 용량재시도 안내와 한도 초기화 시각 확인
시간 초과네트워크, 응답 시간, 요청 크기작은 입력으로 한 번만 분리 점검

키가 잘못됐는지와 주소가 잘못됐는지를 함께 봅니다

발급받은 키가 정상이어도 다른 서비스 주소로 요청하면 인증에 실패합니다. 게이트웨이를 쓸 때는 공급자용 키와 게이트웨이용 키를 혼동하기도 합니다. 로그에 키 원문을 출력하는 대신 요청 호스트, HTTP 상태, 호출 시각을 기록하세요. 키의 앞뒤 공백과 환경변수 이름 오타를 확인하고, 새 키를 발급했다면 실행 중인 프로그램이 새 값을 읽는지도 봅니다.

402와 403은 기다리기만 해서는 풀리지 않을 수 있습니다

OpenRouter 문서는 계정 잔액과 키별 한도뿐 아니라 실행 중인 유료 요청의 예상 비용에 따른 제한도 설명합니다. 조직이 설정한 예산 제한은 403으로 보고될 수 있습니다. 같은 상태 코드라도 오류 메타데이터가 가리키는 제한 주체를 확인해야 합니다. 잔액이 보인다는 이유만으로 계정 전체를 정상이라고 판단하지 마세요.

업무 기록에 “잔액 부족”이라고만 적으면 키 한도를 올렸는지, 동시 요청을 줄였는지 나중에 구분할 수 없습니다. 비밀 값을 제거한 오류 종류, 당시 실행 개수, 출력 상한, 계정 화면의 제한 항목을 함께 남겨보세요. 다른 사람이 같은 문제를 재현하지 않고도 조치 이유를 이해할 수 있습니다.

429에서는 재시도할 때와 멈출 때를 나눕니다

분당 요청 수 초과와 일일 한도 소진은 모두 이용량과 관련되지만 기다려야 하는 시간이 다릅니다. 응답에 Retry-After가 있으면 그 안내를 확인하세요. 일일 한도를 다 쓴 상태라면 몇 초 간격으로 반복해도 해결되지 않습니다. 서비스의 계정 화면이나 한도 API에서 재개 가능한 시점을 확인하고 작업을 중단하는 편이 좋습니다.

자동 처리가 꼭 필요하다면 “최대 세 번만 재시도하고, 실패한 작업은 별도 목록에 저장한다”처럼 종료 조건을 정합니다. 대기 간격을 늘리는 재시도는 일시적인 혼잡을 위한 것이지 인증 실패를 해결하는 방법은 아닙니다. 공급자별 문서에서 실패 요청의 집계 기준도 확인하세요.

시간 초과 후 중복 요청을 조심합니다

클라이언트가 기다리다 멈췄다고 서버의 작업도 반드시 취소된 것은 아닙니다. 자동으로 같은 요청을 연속 전송하기 전에 사용 기록을 확인하세요. 파일별로 작업 ID와 완료 여부를 기록하면 답변을 두 번 저장하는 일을 줄일 수 있습니다. 이메일 발송 같은 후속 동작이 있다면 답변 생성과 실행 승인을 분리해 두는 편이 점검하기 쉽습니다.

재현용 입력은 개인정보가 없는 짧은 문장으로 바꿉니다. 같은 입력이 단일 요청에서는 성공하고 동시 요청에서만 실패한다면 동시 실행 수를 줄이는 실험부터 시작하세요. 결과가 나오면 설정 한 가지씩 바꾸고 원인과 조치를 기록합니다.

키 이름을 알려주는 파일과 키 값을 저장하는 파일을 구분합니다

공유할 설정 예제에는 변수 이름과 설명만 적습니다. 예를 들어 OPENROUTER_API_KEY=본인_키_입력처럼 대체 문구를 쓰고, 실제 값은 개인 환경에서 관리합니다. 환경변수나 .env 파일을 사용한다고 자동으로 안전해지는 것은 아닙니다. 파일을 읽는 라이브러리의 동작과 저장 위치도 확인해야 합니다.

Git을 사용한다면 다음과 같은 제외 규칙을 검토할 수 있습니다. 프로젝트에 따라 폴더 이름은 조정하세요. 이 예제는 새 실습 프로젝트에 적용할 기본 아이디어이며, 기존 프로젝트에 그대로 덮어쓰는 설정은 아닙니다.

이미 Git이 추적하는 파일은 제외 규칙만 추가해도 기록에서 사라지지 않습니다. 커밋 전에 변경 목록과 스테이징된 차이를 직접 확인하세요. 실제 키를 공개했다면 파일 삭제만으로 해결됐다고 판단하지 말고 해당 서비스에서 키를 폐기하고 새 키로 바꿔야 합니다. 과거 커밋이나 복제본에 남은 값도 더 이상 사용할 수 없게 만드는 것이 우선입니다.

입력 자료는 이름만 지운다고 충분하지 않을 수 있습니다

사람 이름을 “고객 A”로 바꿔도 주소, 전화번호, 장비 식별자, 주문번호가 함께 있으면 실제 대상을 알아볼 수 있습니다. 실습에서는 숫자와 상황까지 새로 만든 가상 문서를 사용하는 편이 낫습니다. 도구가 설치됐는지 확인하는 단계에는 실제 계약서나 고객 명단이 필요하지 않습니다.

문서를 외부 AI로 보내기 전에는 이용하려는 서비스뿐 아니라 실제 추론 공급자의 데이터 처리 조건을 확인합니다. 게이트웨이, 모델 공급자, 오류 수집 도구가 각각 어떤 데이터를 받는지 그려보세요. 같은 모델 이름을 선택했더라도 경로와 설정이 바뀌면 확인할 조건도 달라질 수 있습니다.

답변을 저장하지 않아도 로그에 내용이 남을 수 있습니다

디버깅을 위해 요청 본문 전체를 출력하면 입력 문서와 인증 헤더가 로그에 섞일 수 있습니다. 기본 기록 항목은 시각, 모델 ID, 작업 ID, 상태 코드, 소요 시간, 토큰 사용량 정도로 설계해 보세요. 원문이 필요한 오류 분석은 별도로 접근 범위와 삭제 시점을 정하는 편이 관리하기 쉽습니다.

OpenRouter는 자체 입력·출력 저장 설정과 공급자 측 처리를 구분해 설명합니다. 한 서비스의 저장 옵션을 껐다고 모든 경로에서 저장이 사라졌다고 해석하지 마세요. 계정의 관측·개인정보 설정과 공급자 정책을 각각 확인하고, 조직의 문서 취급 기준에 맞는지 판단해야 합니다.

공유 직전의 확인 순서

  1. 실행 파일과 설정 예제에 실제 키가 없는지 확인합니다.
  2. 입력·출력·스크린샷이 모두 가상 데이터인지 확인합니다.
  3. Git 변경 목록과 로그 파일을 확인합니다.
  4. 키 없는 새 폴더에서 설정 설명만 보고 실행 준비가 가능한지 점검합니다.

예제의 재현성을 높이려면 사용한 언어 버전, 모델 선택 방법, 필요한 변수 이름을 함께 적습니다. 실제 비밀 값을 넘기지 않고도 받는 사람이 자신의 계정으로 준비할 수 있는 형태가 좋은 공유 예제입니다.

무료 AI 모델을 업무에 쓰기 전, 같은 입력으로 비교표 만드는 방법

솔루션 비제트 · 평가 설계 노트 · 2026.10.19

모델 추천 글에서 높은 평가를 받았어도 내 문서에서 같은 결과가 나온다는 보장은 없습니다. 업무에 필요한 것은 순위보다 검토 가능한 결과입니다. 여기서는 가상의 장비 점검 메모를 이용해 모델 두 개를 비교하는 평가표를 제안합니다. 아래 점수 기준과 예시는 독자가 직접 적용하도록 만든 양식이며 실제 성능 측정값이 아닙니다.

1. 평가할 입력과 정답을 먼저 만듭니다

다음 문장을 두 모델에 똑같이 넣어보세요. “가상 설비 A의 통신이 오전 9시에 끊겼다. 오전 10시에 통신을 복구했다. 발전량 데이터는 아직 확인하지 못했다. 담당자는 다음 점검 때 데이터 수집 상태를 확인하기로 했다.” 요청은 “확인된 사실, 확인되지 않은 사항, 다음 행동을 구분하라”로 고정합니다.

좋은 답변은 통신이 복구됐다는 사실과 발전량 상태를 모른다는 사실을 구분해야 합니다. “발전이 정상화됐다”거나 구체적인 발전량을 추가하면 입력에 없는 사실을 만든 것입니다. 모델 답변을 본 뒤 기준을 바꾸지 않도록, 평가 전에 금지할 추정과 필수 항목을 적어두세요.

2. 정확성과 형식, 검토 시간을 따로 적습니다

합계가 같아도 중요한 사실을 만들어낸 모델은 해당 업무의 후보에서 제외할 수 있습니다. 점수 합산 전에 “숫자·날짜를 임의로 추가하면 탈락” 같은 필수 조건을 정하세요. 문장이 자연스럽다는 이유만으로 사실 오류를 상쇄하지 않도록 평가 항목을 나누는 것입니다.

3. 짧은 문장만 통과한 결과를 확대하지 않습니다

첫 입력이 끝나면 누락된 날짜가 있는 문서, 서로 다른 장비가 섞인 문서, 불필요한 인사말이 긴 문서를 추가합니다. 각 경우의 기대 결과를 먼저 써두고 모델별로 동일한 설정을 사용하세요. 가능하면 같은 입력을 여러 번 실행해 결과가 흔들리는지도 기록합니다. 몇 번의 성공은 운영 안정성 통계가 아니라 다음 실험으로 넘어갈 근거 정도로 해석하는 편이 적절합니다.

모델 ID, 실행일, 출력 한도, 프롬프트 원문을 함께 저장해야 나중에 비교할 수 있습니다. 무료 모델이 교체되거나 제공 경로가 달라지면 이전 표를 그대로 재사용하지 말고 다시 실행하세요. 긴 문서를 처리할 때는 앞부분과 끝부분의 사실이 모두 보존되는지도 별도로 살펴봅니다.

4. API 요금 외에 전체 처리 시간을 비교합니다

대기, 재시도, 답변 수정까지 포함한 시간을 확인해야 합니다. 아래 숫자는 계산 방식을 설명하기 위한 가상 예시입니다. 직접 정리하면 10분 걸리는 문서가 AI 호출 1분, 검토 7분, 오류 대응 평균 3분을 요구한다면 총 11분입니다. 호출 비용이 없어도 이 작업에서는 시간을 줄이지 못한 셈입니다.

반대로 수정하기 쉬운 구조화된 초안을 꾸준히 만들고 오류를 알아채기 쉽다면 작은 업무부터 적용해 볼 수 있습니다. 자동 발송이나 확정 처리는 뒤로 두고, 사람이 검토하는 초안 단계에서 효과를 확인하세요. 평가표를 남겨두면 모델을 바꿀 때도 같은 기준으로 재검토할 수 있습니다.

보안 설정

윈도우 11 공유폴더 보안 설정 가이드 — 기업 네트워크를 안전하게 지키는 법

솔루션 비제트 · IT 인프라 노트

사무실 여러 대의 PC가 공유폴더로 자료를 주고받는 환경은 업무 효율을 크게 높여주지만, 기본 설정 그대로 사용하면 랜섬웨어나 무단 접근의 통로가 되기도 합니다. 실제로 내부망 침해 사고의 상당수는 외부 침입이 아니라, 느슨하게 열려 있던 공유폴더를 통해 같은 네트워크 안에서 옆으로 퍼져나가는 방식(래터럴 무브먼트)으로 발생합니다.

1. 네트워크 검색과 파일 공유는 '개인 네트워크'에서만 허용하기

윈도우 11의 네트워크 프로필을 공용(Public)이 아닌 개인(Private)으로 정확히 설정하고, 네트워크 검색·파일 및 프린터 공유 기능은 신뢰된 사설망에서만 켜두는 것이 기본입니다. 카페나 외부 공유 와이파이에 노트북을 연결할 때 공용 프로필로 자동 전환되는지 반드시 확인해야 합니다.

2. SMBv1은 반드시 비활성화

과거 대규모 랜섬웨어 확산에 악용됐던 구형 프로토콜인 SMBv1은 특별한 legacy 장비 연동 목적이 아니라면 꺼두는 것이 원칙입니다. '제어판 → 프로그램 → Windows 기능 켜기/끄기'에서 SMB 1.0/CIFS 파일 공유 지원 항목을 해제하면 됩니다.

3. 폴더 단위가 아닌 '계정 단위'로 최소 권한만 부여

모두가 모든 폴더에 접근할 수 있도록 'Everyone'에게 전체 읽기/쓰기 권한을 주는 방식은 편리하지만, 한 계정이 뚫리면 회사 전체 자료가 함께 위험해집니다. 부서·직무별로 필요한 폴더에만 접근하도록 공유 권한과 NTFS 권한을 분리해서 관리하고, 퇴사자 계정은 즉시 회수하는 절차를 마련해야 합니다.

4. 접근 기록은 남기고, 주기적으로 점검한다

누가 언제 어떤 파일에 접근했는지 감사 로그를 남기면, 이상 징후(대량 파일 이동, 새벽 시간대 접근 등)를 빠르게 발견할 수 있습니다. 소규모 조직이라도 분기에 한 번은 공유 권한 목록을 전체 점검해 더 이상 필요 없는 접근 권한이 남아있지 않은지 확인하는 것을 권장합니다.

이런 설정들은 항목이 많고 PC마다 손으로 반복하기 번거롭기 때문에, 저희는 이 과정을 원클릭으로 점검·적용할 수 있는 BZ SMB Settings를 함께 다루고 있습니다. 다만 도구 유무를 떠나, 위 네 가지 원칙만 지켜도 공유폴더발 보안 사고는 상당 부분 예방할 수 있습니다.

태양광 · 에너지

태양광 발전소, 왜 '눈으로 보는' 것만으로는 부족할까 — 원격 모니터링이 필요한 이유

솔루션 비제트 · 에너지 IT 노트

태양광 발전소는 한 번 설치하면 손이 많이 가지 않는 설비로 알려져 있지만, 역설적으로 그 '손이 안 간다'는 특성 때문에 문제가 생겨도 알아채기 어렵습니다. 인버터 한 대가 멈춰도 맑은 날씨에는 패널이 멀쩡히 햇빛을 받고 있는 것처럼 보이기 때문에, 현장을 눈으로만 관리하면 발전량 손실을 몇 주씩 방치하는 일이 실제로 자주 벌어집니다.

발전량(kWh)만 보지 말고 '성능비(PR)'를 봐야 하는 이유

단순 발전량은 날씨 영향을 그대로 받기 때문에, 어제보다 적게 발전했다고 해서 바로 이상이라 판단하기 어렵습니다. 반면 성능비(Performance Ratio)는 일사량 대비 실제 발전량의 비율이므로, 날씨와 무관하게 설비 자체의 건강 상태를 보여주는 지표입니다. PR이 평소보다 꾸준히 낮게 나온다면 오염, 음영, 배선 열화, 인버터 효율 저하 등을 의심해볼 수 있습니다.

인버터 통신 두절 = 골든타임

인버터가 통신을 멈췄다는 것은 단순 통신 장애일 수도 있지만, 실제 고장의 초기 신호인 경우가 많습니다. 이때 즉시 알림을 받을 수 있는 체계가 없다면, 다음 정기 점검일까지 해당 스트링 전체가 발전을 멈춘 채 방치될 수 있습니다. 특히 임야나 지붕형처럼 접근이 쉽지 않은 발전소일수록 원격 알림의 가치가 커집니다.

원격 근무

재택·원격 근무 시대, VPN 하나로 끝내지 말아야 하는 이유

솔루션 비제트 · IT 인프라 노트

원격 근무가 일상화되면서 "VPN만 연결하면 안전하다"는 인식이 널리 퍼져 있습니다. 하지만 VPN은 통신 구간을 암호화해 주는 도구일 뿐, 접속하는 기기 자체가 감염되어 있거나 계정이 탈취된 상황까지 막아주지는 못합니다. 원격 근무 보안은 VPN 하나가 아니라 몇 가지 장치를 함께 갖췄을 때 비로소 완성됩니다.

1. 기기 보안 없이는 VPN도 의미가 없다

백신 미설치, OS 업데이트 방치 상태의 개인 PC로 VPN에 접속하면, 암호화된 터널을 통해 오히려 사내망까지 위협이 그대로 전달될 수 있습니다. 재택근무용 기기는 최소한의 백신과 OS 자동 업데이트가 켜져 있는지부터 확인해야 합니다.

2. 계정 보안: 비밀번호만으로는 부족합니다

VPN·사내 시스템 계정에 다단계 인증(MFA)을 적용하면, 비밀번호가 유출되더라도 실제 침해로 이어질 확률을 크게 낮출 수 있습니다. 문자·앱 인증 중 하나만 추가해도 효과가 큽니다.

3. '어디서든 전체 접근'이 아니라 '필요한 것만 접근'

VPN에 연결되면 사내망 전체에 접근할 수 있도록 설계된 경우, 계정 하나가 뚫리면 피해 범위가 회사 전체로 커집니다. 부서·업무별로 접근 가능한 시스템을 분리하는 최소 권한 원칙을 원격 근무 환경에도 동일하게 적용해야 합니다.

4. 공용 와이파이 사용 원칙을 정해두기

카페, 공항 등 공용 와이파이는 중간자 공격에 취약할 수 있습니다. VPN을 켠 상태에서만 업무 시스템에 접속하도록 원칙을 정하고, 구성원들에게 명확히 안내하는 것만으로도 사고 가능성을 줄일 수 있습니다.

결국 원격 근무 보안은 특정 제품 하나를 도입한다고 끝나는 문제가 아니라, 기기·계정·접근 범위·사용자 습관까지 함께 관리해야 하는 종합적인 과제입니다.

PC 관리

PC가 갑자기 느려졌을 때, 포맷 전에 점검해야 할 5가지

솔루션 비제트 · 컴퓨터 활용 노트

업무용 PC가 눈에 띄게 느려지면 곧바로 포맷부터 고려하는 경우가 많지만, 실제로는 간단한 점검만으로 원인을 찾고 해결되는 경우가 절반 이상입니다. 포맷은 데이터 백업과 프로그램 재설치라는 큰 비용이 따르는 만큼, 아래 순서대로 먼저 점검해보는 것을 권합니다.

1. 시작 프로그램 점검

부팅할 때마다 자동으로 실행되는 프로그램이 많을수록 체감 속도는 크게 떨어집니다. 작업 관리자의 '시작 프로그램' 탭에서 영향이 '높음'으로 표시된 항목 중 당장 필요 없는 것부터 사용 안 함으로 바꿔보세요.

2. 디스크 여유 공간 확인

저장 공간이 90% 이상 차 있으면 운영체제가 임시 파일을 만들 공간이 부족해져 전반적인 속도가 느려집니다. 특히 SSD는 여유 공간이 부족할 때 성능 저하가 더 두드러지므로, 최소 10~15% 이상의 여유 공간을 유지하는 것이 좋습니다.

3. 백그라운드 앱과 동기화 프로그램

클라우드 동기화 프로그램이나 메신저가 백그라운드에서 계속 파일을 스캔·업로드하고 있는 경우가 의외로 많습니다. 작업 관리자에서 CPU·디스크 사용량이 높은 프로세스를 확인해 불필요한 항목을 종료해보세요.

4. 드라이버와 운영체제 업데이트 상태

오래된 그래픽·칩셋 드라이버는 성능 저하는 물론 시스템 불안정의 원인이 되기도 합니다. 제조사 사이트에서 최신 드라이버를 확인하고, 윈도우 업데이트가 장기간 밀려 있지 않은지도 점검해야 합니다.

5. 악성코드 감염 여부

이유 없이 CPU·네트워크 사용량이 계속 높게 유지된다면 악성코드 감염을 의심해볼 필요가 있습니다. 신뢰할 수 있는 백신으로 정밀 검사를 진행해 이상 유무를 먼저 확인하세요.

위 다섯 가지를 점검한 뒤에도 근본적으로 나아지지 않는다면, 하드웨어 노후화나 운영체제 자체의 누적된 문제일 가능성이 높으며, 이때는 포맷 또는 하드웨어 교체를 고려하는 것이 합리적입니다.

"특수문자를 넣고 8자리 이상으로 만들면 안전하다"는 조언은 절반만 맞습니다. 최근 계정 탈취 사고의 상당수는 비밀번호가 단순해서가 아니라, 여러 사이트에서 '같은 비밀번호'를 재사용하다가 그중 한 곳이 유출되면서 발생합니다.

재사용이 가장 큰 위험 요인

한 사이트에서 유출된 아이디·비밀번호 조합은 다른 사이트에 그대로 대입해보는 '크리덴셜 스터핑' 공격에 악용됩니다. 중요도가 높은 계정(이메일, 업무 시스템, 금융)만이라도 서로 다른 비밀번호를 사용하는 것이 단순 복잡도를 높이는 것보다 훨씬 효과적입니다.

비밀번호 관리자 도구를 쓰면 훨씬 쉬워집니다

모든 계정마다 다른 비밀번호를 외우기는 현실적으로 어렵습니다. 비밀번호 관리자를 사용하면 긴 무작위 비밀번호를 계정마다 자동으로 생성·저장할 수 있어, 사용자는 관리자 자체의 마스터 비밀번호 하나만 기억하면 됩니다.

다단계 인증(MFA)은 선택이 아니라 기본값으로

비밀번호가 유출되더라도 다단계 인증이 켜져 있으면 실제 로그인까지 이어지기 어렵습니다. 이메일, 업무용 클라우드 서비스만이라도 우선적으로 MFA를 적용하는 것을 권장합니다.

정기적인 비밀번호 변경보다 '유출 확인'이 더 실용적

특별한 이유 없이 3개월마다 비밀번호를 바꾸도록 강제하는 정책은 오히려 사용자가 예측 가능한 패턴으로 비밀번호를 바꾸게 만들어 실효성이 떨어진다는 연구 결과가 많습니다. 그보다는 내 계정 정보가 유출된 적이 있는지 주기적으로 확인하고, 유출이 확인된 경우에만 즉시 변경하는 방식이 더 실용적입니다.

결국 비밀번호 보안의 핵심은 '얼마나 복잡한가'가 아니라 '얼마나 재사용하지 않는가'와 '얼마나 빨리 유출 사실을 알아채는가'에 있습니다.

데이터 백업

클라우드 백업 vs 로컬 백업, 무엇을 선택해야 할까

솔루션 비제트 · 데이터 관리 노트

"백업은 해두었는데 정작 복구가 안 된다"는 이야기는 생각보다 흔합니다. 많은 경우 원인은 백업을 아예 안 해서가 아니라, 한 가지 방식에만 의존했기 때문입니다. 클라우드와 로컬 백업은 서로 다른 위험을 방어하기 때문에, 원칙적으로는 함께 사용하는 것이 안전합니다.

로컬 백업의 강점과 한계

외장 하드나 NAS를 이용한 로컬 백업은 복구 속도가 빠르고 인터넷 환경에 좌우되지 않는다는 장점이 있습니다. 다만 화재, 침수, 도난처럼 '같은 공간에서 발생하는 재해'에는 원본과 백업본이 동시에 손상될 위험이 있습니다.

클라우드 백업의 강점과 한계

클라우드 백업은 물리적 재해로부터 안전하고 외부 어디서든 접근할 수 있다는 장점이 있지만, 인터넷 회선 속도에 따라 대용량 복구에 시간이 오래 걸릴 수 있고, 랜섬웨어에 감염된 상태로 동기화되면 클라우드상의 파일도 함께 손상될 수 있다는 점을 유의해야 합니다.

실무에서 권장하는 '3-2-1 원칙'

  • 중요 데이터는 최소 3개의 복사본을 유지한다
  • 그중 2개는 서로 다른 저장 매체(예: 내부 디스크 + 외장 디스크)에 보관한다
  • 그중 1개는 물리적으로 다른 장소(클라우드 등 오프사이트)에 보관한다

백업만큼 중요한 '복구 테스트'

백업 파일이 실제로 정상 복구되는지 정기적으로 테스트하지 않으면, 정작 필요한 순간에 손상된 백업본만 남아있는 상황을 맞을 수 있습니다. 분기에 한 번 정도는 샘플 파일을 실제로 복구해보는 절차를 권장합니다.

백업 전략에 정답은 없지만, 원칙은 명확합니다. 한 가지 방식만 믿지 말고, 서로 다른 실패 시나리오를 방어할 수 있도록 이중, 삼중으로 구성하는 것입니다.

업무 생산성

보고서 작성 시간을 절반으로 줄이는 문서 정리 습관

솔루션 비제트 · 업무 효율 노트

같은 업무를 하는데도 누군가는 보고서 작성에 반나절이 걸리고, 누군가는 한 시간이면 끝냅니다. 차이는 글솜씨가 아니라 '평소 자료를 정리해두는 습관'에서 옵니다. 보고서를 쓰기 시작한 다음에 자료를 찾기 시작하면, 이미 절반의 시간을 잃고 시작하는 셈입니다.

1. 폴더 구조는 '내가 찾기 쉬운 대로'가 아니라 '일관된 규칙으로'

개인마다 다른 방식으로 폴더를 만들면, 본인은 익숙해도 팀 전체로 보면 자료를 찾는 데 시간이 더 걸립니다. 연도-분기-프로젝트명처럼 팀 전체가 동일하게 적용할 수 있는 단순한 규칙 하나를 정해두는 것이 훨씬 효율적입니다.

2. 회의록은 회의 직후 5분 안에 정리

회의가 끝난 직후 핵심 결정사항과 담당자, 기한만이라도 5분 안에 정리해두면, 며칠 뒤 보고서를 쓸 때 기억에 의존하지 않고 바로 인용할 수 있습니다. 미루면 미룰수록 복원하는 데 걸리는 시간이 기하급수적으로 늘어납니다.

3. 반복되는 보고서는 '템플릿화'하기

매주·매월 형식이 비슷한 보고서를 매번 새로 작성하고 있다면, 공통 항목을 템플릿으로 만들어두는 것만으로 작성 시간을 크게 줄일 수 있습니다. 바뀌는 숫자와 코멘트만 채워 넣는 구조로 바꿔보세요.

4. 데이터는 '캡처'가 아니라 '원본 링크'로 남기기

화면 캡처 이미지만 저장해두면 나중에 값이 바뀌었을 때 다시 찾아야 합니다. 가능하다면 원본 파일이나 시트에 대한 링크를 함께 기록해두는 습관을 들이면, 최신 데이터를 다시 확인하는 시간을 크게 줄일 수 있습니다.

결국 보고서 작성 속도를 높이는 가장 확실한 방법은 글쓰기 실력을 키우는 것이 아니라, 평소 자료가 흩어지지 않도록 정리하는 습관을 팀 전체가 함께 만드는 것입니다.

프로그램 비교

압축 프로그램 뭐 써야 할까 — 알집·반디집·7-Zip 비교

솔루션 비제트 · 프로그램 활용 노트

압축 프로그램은 한 번 설치하면 잘 바꾸지 않는 프로그램 중 하나지만, 세 프로그램은 라이선스 정책과 사용 방식에서 분명한 차이가 있습니다. 용도에 맞게 고르면 불필요한 결제나 광고 노출 없이 더 편하게 쓸 수 있습니다.

알집(ALZip)

국내에서 가장 오래 쓰인 압축 프로그램 중 하나로, 한글 파일명 처리와 국내 사용 환경에 맞춘 인터페이스가 특징입니다. 가정용은 무료로 제공되지만 기업에서 영리 목적으로 사용할 경우 별도의 유료 라이선스가 필요하다는 점을 꼭 확인해야 합니다.

반디집(Bandizip)

가볍고 빠른 압축·해제 속도로 알려져 있으며, 개인 사용자뿐 아니라 상업적 용도로도 무료로 사용할 수 있다는 점이 큰 장점입니다. ZIP, 7Z, RAR 등 주요 압축 포맷을 폭넓게 지원하고, 미리보기 기능이 강점으로 꼽힙니다.

7-Zip

오픈소스 기반의 압축 프로그램으로, 완전 무료이며 상업적 이용에도 제약이 없습니다. 자체 포맷인 7z는 같은 데이터 기준으로 압축률이 높은 편으로 알려져 있으며, 명령줄(CLI) 지원이 되어 개발자나 자동화 스크립트에서도 활용하기 좋습니다. 다만 인터페이스는 상대적으로 단순한 편입니다.

정리하면

  • 가볍고 무료로 상업적 이용까지 하고 싶다면 → 반디집 또는 7-Zip
  • 높은 압축률과 명령줄 자동화가 필요하다면 → 7-Zip
  • 익숙한 국내 인터페이스가 우선이라면 → 알집(단, 기업 사용 시 라이선스 확인 필수)

어떤 프로그램을 쓰든, 회사에서 사용하는 소프트웨어라면 반드시 라이선스 정책을 먼저 확인하는 습관이 중요합니다. 무료로 알려진 프로그램도 상업적 이용 범위가 제한되어 있는 경우가 적지 않습니다.

업무 도구

클라우드 오피스 vs 설치형 오피스, 우리 조직엔 뭐가 맞을까

솔루션 비제트 · 업무 도구 노트

문서 작업 도구를 고를 때 가장 많이 비교되는 것이 구글 워크스페이스(Google Workspace) 같은 클라우드 오피스와, 마이크로소프트 오피스 같은 설치형 오피스입니다. 두 방식은 우열의 문제가 아니라 업무 방식에 따른 적합도의 문제입니다.

클라우드 오피스가 유리한 경우

여러 명이 동시에 한 문서를 편집하거나, 외부 협업이 잦거나, 재택·외근이 많은 조직이라면 실시간 공동 편집과 어디서나 접속 가능한 클라우드 오피스가 유리합니다. 버전 충돌 걱정 없이 항상 최신 문서를 유지할 수 있다는 것도 큰 장점입니다.

설치형 오피스가 유리한 경우

복잡한 수식이 많은 대용량 엑셀 작업, 정교한 인쇄 레이아웃이 필요한 문서, 인터넷 연결이 불안정한 현장 환경이라면 아직은 설치형 오피스의 처리 속도와 기능 완성도가 더 안정적인 경우가 많습니다.

혼합 운영도 현실적인 선택입니다

실제로는 두 방식을 완전히 하나로 통일하기보다, 협업·회의 문서는 클라우드 오피스로, 정산·보고용 대용량 문서는 설치형 오피스로 나눠 쓰는 조직도 많습니다. 도구를 하나로 강제 통일하기보다 업무 성격에 맞게 병행하는 것이 현실적인 해법이 될 수 있습니다.

어떤 도구를 선택하든 중요한 것은 구성원 전체가 같은 방식으로 문서를 저장·공유하는 규칙을 갖추는 것입니다. 도구가 달라도 규칙이 없으면 결국 파일을 못 찾는 문제는 똑같이 반복됩니다.

컴퓨터 활용

노트북 배터리 수명, 충전 습관만 바꿔도 오래갑니다

솔루션 비제트 · 컴퓨터 활용 노트

노트북 배터리는 소모품이라 언젠가는 교체가 필요하지만, 충전 습관에 따라 그 시점을 1~2년 이상 늦출 수 있습니다. 대부분의 리튬이온 배터리는 완전 충전과 완전 방전을 반복할수록 수명이 빨리 줄어드는 특성이 있습니다.

0%와 100%를 자주 오가지 않기

배터리를 완전히 방전시킨 뒤 100%까지 꽉 채우는 습관보다는, 20~80% 구간을 유지하며 충전하는 것이 배터리 수명에 더 유리한 것으로 알려져 있습니다. 최근 출시되는 노트북은 충전 상한선을 설정할 수 있는 기능을 제공하는 경우가 많으니 활용해볼 만합니다.

고온 환경을 피하기

배터리는 열에 특히 취약합니다. 노트북을 이불이나 쿠션 위에 올려두고 장시간 사용하면 내부 온도가 올라가면서 배터리 열화가 빨라집니다. 통풍이 되는 딱딱한 바닥에서 사용하는 것만으로도 배터리 수명에 도움이 됩니다.

장기간 보관할 땐 50% 내외로

노트북을 오래 사용하지 않고 보관해야 한다면, 완전 충전이나 완전 방전 상태보다 50% 내외로 충전해둔 뒤 보관하는 것이 배터리에 더 안전합니다.

작은 습관이지만, 배터리 교체 비용과 업무 중단 리스크를 함께 줄여준다는 점에서 장비를 관리하는 조직이라면 구성원들에게 안내할 만한 내용입니다.

보안 인식

이메일 피싱, 이런 패턴이면 일단 의심하세요

솔루션 비제트 · 보안 인식 노트

피싱 메일은 더 이상 어색한 번역투 문장으로만 오지 않습니다. 실제 거래처나 상사의 말투를 흉내 낸 정교한 메일이 늘면서, 기술적 차단만큼이나 '사람이 먼저 알아채는 능력'이 중요해졌습니다.

1. 발신자 표시 이름과 실제 주소가 다르다

메일 클라이언트에 표시되는 이름은 얼마든지 조작할 수 있습니다. 발신자 이름이 익숙하더라도, 실제 이메일 주소(@ 뒤 도메인)가 평소 쓰던 주소와 미묘하게 다르지는 않은지 반드시 확인하는 습관이 필요합니다.

2. 급하게 재촉하는 문구
